### SREV-122: Process Force Map Allocation Lifetime

| Field | Content |
|---|---|
| Severity | [major] |
| Status | patched source-level after official kernel pool-allocation, resource-lock, and IRQL shape; needs Windows driver build/fault-injection proof |
| Evidence | `Sandboxie/core/drv/process_force.c` was the highest-ranked unnamed reviewable core file after SREV-121. `Process_DfpInsert` allocated `FORCE_PROCESS_2` records for `Process_MapDfp` and immediately wrote `proc->pid` / `proc->silent`; `Process_FcpInsert` allocated `FORCE_PROCESS_3` records for `Process_MapFcp` and immediately wrote `proc->pid` / `proc->boxname`. The local `Mem_Alloc` backend can return `NULL`, matching the official Windows pool-allocation failure shape. A failed allocation would therefore null-dereference while DFP/FCP process-map insertion was in progress, including self-locked paths that had raised IRQL and acquired `Process_ListLock`. |
| Data | `Process_DfpInsert`, `Process_FcpInsert`, `Process_DfpDelete`, `Process_FcpDelete`, `Process_MapDfp`, `Process_MapFcp`, `FORCE_PROCESS_2`, `FORCE_PROCESS_3`, `Mem_Alloc`, `map_insert`, `Process_ListLock`, `KeRaiseIrql`, `KeLowerIrql`, `ExAcquireResourceExclusiveLite`, `ExReleaseResourceLite`, `PROCESS_TERMINATED`, `pid`, `silent`, and `boxname`. |
| Schema | `PROCESS_FORCE_MAP_ALLOCATION_LIFETIME` says `Mem_Alloc` may return `NULL` because pool allocation can fail; `Process_DfpInsert(PROCESS_TERMINATED, ProcessId)` owns the DFP record allocation while it holds `Process_ListLock`, and allocation failure releases `Process_ListLock`, restores IRQL, and returns `FALSE`; `Process_DfpInsert(ParentId, ProcessId)` is called with the process list already locked, and child allocation failure returns `FALSE` without inserting a map record; `Process_FcpInsert` owns the FCP record allocation while it holds `Process_ListLock`, and allocation failure releases `Process_ListLock`, restores IRQL, and returns; DFP/FCP delete, check, map key, silent flag, box-name copy, and force-policy semantics are unchanged. |
| Topology | `Session_Api_DisableForce` calls `Process_DfpInsert(PROCESS_TERMINATED, ProcessId)`, which raises IRQL, acquires `Process_ListLock`, deletes any old DFP record, allocates `FORCE_PROCESS_2`, inserts it into `Process_MapDfp`, then releases the lock and restores IRQL; allocation failure now exits through the same lock/IRQL owner. `Process_NotifyProcess_Create` calls `Process_DfpInsert(ParentId, ProcessId)` while already owning the process-list lock; allocation failure returns `FALSE` to that caller-owned lock scope. `Session_Api_ForceChildren` calls `Process_FcpInsert`, which mirrors the self-locked DFP lifetime for `FORCE_PROCESS_3` and `Process_MapFcp`. |
| Logic Risk | Force-process state is checked on process creation and session API paths, so low-memory failures must fail closed without crashing the driver or leaving `Process_ListLock`/IRQL ownership unbalanced. The old code treated map-record allocation as infallible and wrote through a possibly null pointer. The correct local repair is an allocation lifetime gate at the map-record owner boundary, not a change to force-process policy, force-children semantics, map keys, delete/check behavior, or alert routing. |
| Official Shape | `docs/plan/srev-122-process-force-map-allocation-lifetime.md` records Microsoft `ExAllocatePoolWithTag`, `ExAcquireResourceExclusiveLite`, `ExReleaseResourceLite`, `KeRaiseIrql`, and `KeLowerIrql` references. `docs/plan/srev-122-process-force-map-allocation-lifetime.schema.json` records the JSON Schema draft-07 local `PROCESS_FORCE_MAP_ALLOCATION_LIFETIME` contract. |
| Fix | `Process_DfpInsert(PROCESS_TERMINATED, ProcessId)` now checks the `FORCE_PROCESS_2` allocation before writing fields or inserting into `Process_MapDfp`; on failure it releases `Process_ListLock`, lowers IRQL, and returns `FALSE`. `Process_DfpInsert(ParentId, ProcessId)` now checks the child `FORCE_PROCESS_2` allocation before writing fields or inserting into `Process_MapDfp`; on failure it returns `FALSE` to the already-locked caller. `Process_FcpInsert` now checks the `FORCE_PROCESS_3` allocation before writing fields or inserting into `Process_MapFcp`; on failure it releases `Process_ListLock`, lowers IRQL, and returns. No DFP/FCP map key, delete path, check path, silent flag behavior, box-name copy shape, force-alert policy, force-children policy, or process-list lock ownership changed. |
| Acceptance Gate | `docs/plan/check-srev-122.py` validates the draft-07 schema, official references, local nullable pool allocation shape, `Process_DfpInsert(PROCESS_TERMINATED, ...)` allocation gate before field writes with balanced lock/IRQL release, parent-child DFP allocation gate before field writes with caller-lock ownership preserved, `Process_FcpInsert` allocation gate before field writes with balanced lock/IRQL release, stale unguarded allocation/write patterns removed, and ledger entry; `docs/plan/check-srev-122.sh` is the matrix wrapper. Runtime/build gate: Windows driver build for `process_force.c`, pool-allocation failure injection for each DFP/FCP insertion path, lock/IRQL balance observation on self-locked failures, no-null-map-insert observation on caller-locked DFP failure, and positive DFP/FCP smoke proving unchanged insert, check, delete, silent flag, and box-name propagation behavior. |
