### SREV-117: Process Util Allocation Lifetime

| Field | Content |
|---|---|
| Severity | [major] |
| Status | patched source-level after official pool-allocation, system-thread, handle-close, and string-format shape; needs Windows driver build/fault-injection proof |
| Evidence | `Sandboxie/core/drv/process_util.c` was the highest-ranked unnamed reviewable core file after SREV-116. `Process_ScheduleKill` allocated a two-slot context with `Mem_Alloc(Driver_Pool, sizeof(PVOID)*2)`, immediately wrote `params[0]` and `params[1]`, and then passed the context to `PsCreateSystemThread`. The local pool backend can return `NULL`. If allocation failed, the old code dereferenced NULL. If `PsCreateSystemThread` failed after allocation, no worker owned the context and the caller returned `FALSE` without freeing it. `Process_LogMessage` similarly allocated transient log text and then called `RtlStringCbPrintfW` without checking the allocation result. |
| Data | `Process_LogMessage`, `Process_ScheduleKill`, `Process_ScheduleKillProc`, `Mem_Alloc`, `Mem_Free`, `RtlStringCbPrintfW`, `PsCreateSystemThread`, `ZwClose`, `PsTerminateSystemThread`, `Driver_Pool`, `proc->pool`, log text buffer, two-slot kill context, returned system-thread handle, and worker start context. |
| Schema | `PROCESS_UTIL_ALLOCATION_LIFETIME` says `Mem_Alloc` may return `NULL` because its pool backend may fail allocation; any buffer passed to `RtlStringCbPrintfW` must be allocated before use; `Process_LogMessage` may skip logging when transient log-text allocation fails; `Process_ScheduleKill` owns the two-slot thread context until `PsCreateSystemThread` succeeds; after `PsCreateSystemThread` succeeds, `Process_ScheduleKillProc` owns and frees the thread context; if `PsCreateSystemThread` fails, `Process_ScheduleKill` frees the thread context and returns `FALSE`; the returned system-thread handle remains closed by the caller after successful `PsCreateSystemThread`; this SREV does not change termination policy, delay/retry behavior, process handle access masks, service-cancel fallback, log message ids, or worker termination status. |
| Topology | `Process_LogMessage` flows through transient pool allocation, allocation gate, `RtlStringCbPrintfW`, `Log_MsgP1`, and `Mem_Free`. `Process_ScheduleKill` flows through Driver_Pool context allocation, allocation gate, context fill, `PsCreateSystemThread`, caller-side `ZwClose(handle)` on success, worker-side context free in `Process_ScheduleKillProc`, or caller-side context free on thread-create failure. |
| Logic Risk | Termination and logging paths often run when the system is already under pressure. Treating allocation as infallible converts low-memory handling into a kernel crash. Treating `PsCreateSystemThread` as an unconditional ownership transfer leaks the context when thread creation fails. The correct local fix is a lifetime gate, not a policy change to who may be killed, which process access mask is used, or how delayed retry works. |
| Official Shape | `docs/plan/srev-117-process-util-allocation-lifetime.md` records Microsoft `ExAllocatePoolWithTag`, `PsCreateSystemThread`, `ZwClose`, and `RtlStringCbPrintfW` references. `docs/plan/srev-117-process-util-allocation-lifetime.schema.json` records the JSON Schema draft-07 local `PROCESS_UTIL_ALLOCATION_LIFETIME` contract. |
| Fix | `Process_LogMessage` now returns without logging if transient log-text allocation fails. `Process_ScheduleKill` now returns `FALSE` if the two-slot worker context cannot be allocated, and frees that context with `Mem_Free(params, sizeof(PVOID)*2)` if `PsCreateSystemThread` fails after allocation. The successful path is unchanged: caller closes the returned system-thread handle, worker frees the context at entry, and normal immediate/delayed kill behavior remains intact. |
| Acceptance Gate | `docs/plan/check-srev-117.py` validates the draft-07 schema, official references, nullable pool allocation shape, `Process_LogMessage` allocation-before-format gate, `Process_ScheduleKill` context allocation gate, caller-side free on `PsCreateSystemThread` failure, worker-side context free on successful transfer, successful thread-handle close, and ledger entry; `docs/plan/check-srev-117.sh` is the matrix wrapper. Runtime/build gate: Windows driver build for `process_util.c`, pool allocation failure injection for log and schedule-kill paths, `PsCreateSystemThread` failure injection after context allocation, and normal immediate/delayed kill smoke proving the thread handle is closed and context is freed by the worker. |
