## Evidence

The Avast/SnxHk compatibility hook intercepts `LdrGetProcedureAddress` for
`ntdll!NtDeviceIoControlFile` and returns a generated executable trampoline
instead of the Sandboxie-hooked native stub. The local reason is that the Avast
hook DLL copies code bytes and does not fix relative jump operands.

Before this SREV, the code published the static `code` pointer before writing
the trampoline bytes and returned it without an instruction-cache boundary:

```text
code = Dll_AllocCode128()
write executable bytes through code
*Address = code
```

Official references:

- https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-flushinstructioncache
- https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc

Adjacent SREV coverage:

- SREV-058 defines the local DLL hook instruction-cache coherency contract.
- SREV-247 applies the same publication gate shape to a generated WOW64 stub.

## Data

`Custom_Avast_SnxHk_LdrGetProcedureAddress`, `__sys_LdrGetProcedureAddress`,
`Dll_Ntdll`, `NtDeviceIoControlFile`, `Dll_AllocCode128`, generated x86/x64
absolute-jump trampoline bytes, `FlushInstructionCache`, static `code`, and
the returned `Address` output slot.

## Schema

`CUSTOM_AVAST_TRAMPOLINE_PUBLISH_GATE` says:

- the Avast compatibility path owns one generated executable trampoline for
  `ntdll!NtDeviceIoControlFile`;
- generated executable bytes must be written through a local unpublished pointer;
- the generated code range must be flushed before publication through static
  `code` or the returned `Address` output slot;
- allocation failure must return the native lookup status without writing
  through a null trampoline pointer;
- this SREV does not change hook selection, `LdrGetProcedureAddress` forwarding,
  target API name matching, or generated x86/x64 trampoline bytes.

## Topology

```text
LdrGetProcedureAddress(ntdll, "NtDeviceIoControlFile")
  -> native lookup gives hooked address
  -> allocate executable code slot
  -> write absolute-jump trampoline through unpublished local pointer
  -> FlushInstructionCache(local pointer, generated byte span)
  -> publish static code pointer
  -> return published pointer through Address
```

## Logic Risk

Publishing `code` before writing the bytes allows a racing call to observe a
non-null static pointer whose executable contents are not complete. Returning a
generated executable stub without flushing the instruction cache violates the
same execution boundary already recorded by SREV-058 and SREV-247.

## Fix

The code now writes through a local `new_code` pointer, gates null allocation,
flushes the generated 12-byte range, and only then assigns `code = new_code`.
The returned trampoline byte sequence and target matching are unchanged.
