## Evidence

SREV-247 already owns the pre-Windows 10 WOW64 stub publication gate:
allocation gate, 13-byte generated executable code, instruction-cache flush,
and publication through `fs:[0xC0]`.

The remaining source comment was only an instruction shorthand:

```text
and eax, 0xFFFF ; xor ecx, ecx ; jmp xxx ( push xxx; ret; )
```

That shorthand did not name the owner, byte-span, or publication gate.

## Data

`Dll_FixWow64Syscall`, `_code`, 13-byte pre-Windows 10 WOW64 stub,
`X86SwitchTo64BitMode`, `FlushInstructionCache`, `__writefsdword(0xC0, ...)`,
and SREV-247.

## Schema

`DLLHOOK_WOW64_STUB_COMMENT_OWNER` says:

- SREV-247 owns the 13-byte pre-Windows 10 WOW64 stub layout and publication
  gate;
- the source comment must name that owner and the stub byte layout intent;
- this SREV does not change allocation, generated bytes, flush ordering,
  publication edge, Windows 10 path, or WOW64 hook policy.

## Topology

```text
SREV-247 13-byte stub owner
  -> write pre-Windows 10 WOW64 transition stub
  -> FlushInstructionCache(_code, 13)
  -> __writefsdword(0xC0, _code)
```

## Logic Risk

Mnemonic-only comments are easy to treat as local folklore. This byte sequence
is part of a publication contract: the owner is SREV-247, and any future change
must preserve or reprove the stub layout, cache boundary, and thread-local
publication edge.

## Fix

Comment-only source clarification. The source now says SREV-247 owns the
13-byte pre-Windows 10 WOW64 stub and keeps the mnemonic as byte-layout intent.
No behavior changed.

## Acceptance Gate

`docs/plan/check-srev-261.py` validates the draft-07 schema, source comment,
unchanged generated byte sequence, SREV-247 adjacency, and the ledger fragment.

Runtime gate: inherited from SREV-247.
