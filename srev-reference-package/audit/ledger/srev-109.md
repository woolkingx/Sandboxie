### SREV-109: MountManager ImBox State Boundaries

| Field | Content |
|---|---|
| Severity | [major] |
| Status | source-level classified after official mounted-folder, reparse-point, DOS-device, logical-drive, and volume mount-point enumeration shape; comment-only source clarification, no behavior change |
| Evidence | `Sandboxie/core/svc/MountManager.cpp` owns ImBox-backed encrypted image / ramdisk mount state. The uncovered comments named mounted-disk discovery, unsupported image update, recovered-device protection query, mounting without a drive letter, and automatic `BoxPassword` use. Microsoft documents mounted folders as volume-to-directory associations, reparse points as tagged caller data with strict buffer/tag/empty-directory rules, `DefineDosDeviceW` as MS-DOS device namespace mapping, and mounted-folder enumeration as volume-scoped. Local source shows the missing state is Sandboxie-specific: `m_RootMap` requires `reg_root` and `file_root`, `BOX_MOUNT::Protected` is set only after `API_PROTECT_ROOT`, `FindImDisk` recovers only `NtPath` / `ImageFile` by ImBox proxy name, `MountImDisk` formats through a temporary drive letter and removes it when not requested, and passwords are request-supplied rather than read from durable config. |
| Data | `MountManager::MountHandler`, `MountManager::AcquireBoxRoot`, `MountManager::FindImDisk`, `MountManager::MountImDisk`, `MountManager::UpdateHandler`, `CreateJunction`, `RemoveJunction`, `BOX_MOUNT`, `BOX_ROOT`, `m_RootMap`, `m_RamDisk`, `IMBOX_MOUNT_REQ`, `IMBOX_UPDATE_REQ`, `SbieDll_Mount`, `req->password`, `API_PROTECT_ROOT`, `API_UNPROTECT_ROOT`, `ImDiskGetDeviceListEx`, `ImDiskQueryDeviceProxy`, `ImDiskFindFreeDriveLetter`, `GetLogicalDrives`, `DefineDosDevice`, `FSCTL_SET_REPARSE_POINT`, `FSCTL_DELETE_REPARSE_POINT`, and `BoxPassword`. |
| Schema | `MOUNTMANAGER_IMBOX_STATE_BOUNDARIES` says the constructor does not rebuild `m_RootMap` from devices alone; `FindImDisk` recovers only ImDisk device identity by proxy name; `reg_root` and `file_root` ownership comes from `IMBOX_MOUNT` or `AcquireBoxRoot` requests; `BOX_MOUNT::Protected` becomes true only after `API_PROTECT_ROOT` succeeds; recovered ImDisk devices do not imply protected-root state; `IMBOX_UPDATE` remains unsupported until resize/password rotation has a transaction contract; `MountImDisk` requires a temporary drive-letter path for initial format; unrequested drive-letter mappings are removed after device discovery; `BoxPassword` is not read from durable config in `AcquireBoxRoot`; encrypted image mounts require caller-supplied password until secure handoff exists. |
| Topology | Explicit mounts flow from `SbieDll_Mount` / `IMBOX_MOUNT_REQ` to `MountHandler`, then `FindImDisk` or `MountImDisk`, optional `API_PROTECT_ROOT`, `m_RootMap[reg_root]`, and `CreateJunction(nt_path\\Sandbox, file_root)`. Automatic acquisition flows from `AcquireBoxRoot` through `UseRamDisk` / `UseFileImage`, certificate option checks, `FindImDisk` or `MountImDisk`, and the same root/junction path. `MountImDisk` chooses a requested or free drive letter, launches `ImBox.exe` with `mount=<drive>` and `format=ntfs`, passes password through locked remote memory, reads the returned `\\Device\\ImDiskN`, and removes the DOS-device mapping with `DefineDosDevice(... DDD_REMOVE_DEFINITION | DDD_EXACT_MATCH_ON_REMOVE | DDD_RAW_TARGET_PATH ...)` when the drive letter was temporary. |
| Logic Risk | Treating these TODOs as independent local chores would create false state. Rebuilding roots from devices alone loses registry-root ownership and protection policy. A driver-side protected-state query would need a scoped reg-root/device contract. "Mount without mount" conflicts with the current ImBox/fmifs formatting path. Reading `BoxPassword` from durable config would weaken the explicit credential handoff and needs a separate secure storage design. `IMBOX_UPDATE` declares wire fields but lacks a resize/password-rotation transaction that coordinates ImBox state, image data, protection state, and failure rollback. |
| Official Shape | `docs/plan/srev-109-mountmanager-imbox-state-boundaries.md` records Microsoft mounted-folder, reparse-point, `FSCTL_SET_REPARSE_POINT`, `FSCTL_GET_REPARSE_POINT`, `FSCTL_DELETE_REPARSE_POINT`, `DeviceIoControl`, `GetLogicalDrives`, `DefineDosDeviceW`, and mounted-folder enumeration references. `docs/plan/srev-109-mountmanager-imbox-state-boundaries.schema.json` records the JSON Schema draft-07 local `MOUNTMANAGER_IMBOX_STATE_BOUNDARIES` contract. |
| Fix | Comment-only source clarification: constructor recovery is lazy through `FindImDisk` and cannot rebuild `m_RootMap`; `IMBOX_UPDATE` remains unsupported until a transaction/protection refresh contract exists; recovered devices do not restore `Protected` without explicit `API_PROTECT_ROOT`; temporary drive-letter use is required by the current ImBox format path; and `AcquireBoxRoot` does not read durable `BoxPassword` before a secure credential handoff exists. No mount, unmount, ImDisk enumeration, `DefineDosDevice`, reparse-point, password passing, driver protection, or wire-message behavior changed. |
| Acceptance Gate | `docs/plan/check-srev-109.py` validates the draft-07 schema, official references, removal of uncovered TODO comments, MountManager source comments, explicit mount/acquire/recovery topology, temporary drive-letter cleanup, unsupported update behavior, and ledger entry; `docs/plan/check-srev-109.sh` is the matrix wrapper. Runtime gate: Windows matrix with explicit encrypted image mount, automatic `UseFileImage`, `UseRamDisk`, service restart with existing ImDisk device, `protect_root` true/false, `admin_only` true/false, temporary drive-letter allocation/removal, requested drive-letter preservation, `FSCTL_SET_REPARSE_POINT` and `FSCTL_DELETE_REPARSE_POINT` behavior on empty/non-empty file roots, and negative proof that `IMBOX_UPDATE` remains unsupported. |
