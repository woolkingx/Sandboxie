### SREV-092: SCM MSI Loader Unload Event Owner

| Field | Content |
|---|---|
| Severity | [major] |
| Status | patched source-level after official `LdrRegisterDllNotification`, `LdrDllNotification`, MSI handle close, and named-event shape; needs Windows MSI runtime proof |
| Evidence | `Sandboxie/core/dll/scm_msi.c` creates `SBIE_WindowsInstallerInUse` when `msi.dll` loads so the sandboxed MSI server can stay alive while a client process uses MSI. Microsoft documents `LdrDllNotification` as having load and unload reasons. Microsoft documents `MsiCloseHandle` as closing one installation handle from the same creating thread, and documents `MsiCloseAllHandles` as diagnostic rather than cleanup. |
| Data | `msi.dll` load/unload state, `Scm_MsiDll` module init, `Msi_ServerInUseEvent`, `SBIE_WindowsInstallerInUse` named event, sandboxed MSI server waiter, `MsiCloseHandle`, and `MsiCloseAllHandles`. |
| Schema | `SCM_MSI_LOADER_UNLOAD_EVENT_OWNER` says `msi.dll` load may create the `SBIE_WindowsInstallerInUse` named event; loader unload notifications are recorded by the Ldr layer; sub-module init functions are called on load and `unload_func` is optional; `Scm_MsiDll(NULL)` unload cleanup releases the process event hold created on `msi.dll` load; `MsiCloseHandle` is per-thread/per-handle and is not a proven last-MSI-session owner; `MsiCloseAllHandles` is diagnostic and must not become cleanup owner; the MSI server waiter exits only when the named in-use event no longer opens; runtime capture must prove the edge across MSI module lifetime, installer handles, custom actions, and MSIServer lifetime before merging/releasing behavior. |
| Topology | `msi.dll` load crosses into `Ldr_MyDllCallbackNew(load)`, calls `Scm_MsiDll(ImageBase)`, and creates the named in-use event. The sandboxed MSI server calls `Scm_SetupMsiWaiter` and exits when `OpenEvent` for that name fails. `msi.dll` unload crosses into `Ldr_MyDllCallbackNew(unload)`, calls the optional `dll->unload_func(NULL)` for the `msi.dll` row, enters `Scm_MsiDll(NULL)`, closes `Msi_ServerInUseEvent`, clears the handle, then clears local loader state and unhooks the module. |
| Logic Risk | The old comment correctly noticed a lifetime gap but proposed an unproven owner. Hooking `MsiCloseHandle` as a release signal would be wrong without runtime proof because it closes one thread-owned installer handle, not the process's last MSI user/session. The source-level path now uses the module lifetime edge, but Windows MSI runtime still has to prove it does not drop the event while custom actions or installer handles remain active. |
| Official Shape | `docs/plan/srev-092-scm-msi-loader-unload-event-owner.md` records Microsoft `LdrRegisterDllNotification`, `LdrDllNotification`, `MsiCloseHandle`, `MsiCloseAllHandles`, event objects, `CreateEventW`, and `CloseHandle` references. `docs/plan/srev-092-scm-msi-loader-unload-event-owner.schema.json` records the JSON Schema draft-07 local `SCM_MSI_LOADER_UNLOAD_EVENT_OWNER` contract. |
| Runtime Capture Matrix | Windows 10/11 build number, install/repair/uninstall/advertised repair/custom-action entry paths, one-client/multi-client/nested-custom-action/early-crash process shapes, `msi.dll` load/unload notifications, `Ldr_MyDllCallbackNew` load/unload state, `CreateEvent(SBIE_WindowsInstallerInUse)`, MSI server `OpenEvent` success/failure, last handle close, `CloseHandle(Msi_ServerInUseEvent)`, MSI handle APIs, sandboxed MSIServer start, waiter polling, last-user exit, non-exit while installer handles or custom actions remain, and negative controls for per-thread handle close, cross-thread handles, `MsiCloseAllHandles`, active transaction unload, failed event creation, and non-MSI DLL churn. |
| Shared Runtime Capture Evidence | Runtime records use `docs/plan/srev-092-322-user-lifecycle-runtime-capture.schema.json` with feature path `msi-last-user-event`; `docs/plan/srev-092-322-user-lifecycle-runtime-capture-playbook.md` is the capture procedure; `docs/plan/check-srev-092-322-user-lifecycle-runtime-capture.sh` validates the shared user-mode lifecycle evidence contract. |
| Fix | Source-level event-release path: `Ldr_Dlls` now has an optional `unload_func` slot. The `msi.dll` row wires that slot to `Scm_MsiDll`, and `Ldr_MyDllCallbackNew(unload)` calls `dll->unload_func(NULL)` before clearing module state. `Scm_MsiDll(NULL)` closes `Msi_ServerInUseEvent` and clears the handle. `MsiCloseHandle` remains explicitly outside the event-owner path. |
| Acceptance Gate | `docs/plan/check-srev-092.py` validates the draft-07 schema, official references, `msi.dll -> Scm_MsiDll` load registration, optional `unload_func` topology, `msi.dll -> Scm_MsiDll(NULL)` unload routing, stale `XXX` / disabled branch removal, named-event creation, event close/clear on unload, MSI server waiter behavior, concrete runtime capture matrix, and ledger entry; `docs/plan/check-srev-092.sh` is the targeted wrapper. Windows gate: MSI runtime matrix proving a true last-user edge for client MSI processes across module lifetime, installer handles, custom actions, and MSIServer lifetime, while verifying that sandboxed MSIServer exits after the last real MSI user without exiting while custom actions or installer handles remain active. Windows gate: validate captured MSI lifecycle records against the shared user-mode lifecycle schema before release. |
