# SREV-247: DLL Hook WOW64 Stub Publish Gate

## Stage Gate

| Field | Value |
|---|---|
| Stage | schema -> topology -> logic -> action -> verify |
| Input artifact | `Sandboxie/core/dll/dllhook.c`, `Sandboxie/core/dll/dllmem.c`, Microsoft executable-code references |
| Output artifact | `docs/plan/srev-247-dllhook-wow64-stub-publish-gate.schema.json`, `docs/plan/check-srev-247.py`, `docs/plan/check-srev-247.sh`, ledger fragment, owner-local source patch |
| Owner | pre-Windows 10 WOW64 `fs:[0xC0]` stub publishing in `Dll_FixWow64Syscall` |

## Evidence

The pre-Windows 10 WOW64 path in `Dll_FixWow64Syscall` builds a 13-byte
executable stub, then publishes it into the thread-specific WOW64 transition
slot with `__writefsdword(0xC0, (ULONG)_code)`.

Before this SREV, the code did this:

```c
_code = (UCHAR *)Dll_AllocCode128();
*(ULONG *)(_code + 0) = 0xFF25C933;
*(ULONG *)(_code + 4) = 0x680000FF;
*(ULONG *)(_code + 8) = X86SwitchTo64BitMode;
*(UCHAR *)(_code + 12) = 0xc3;
__writefsdword(0xC0, (ULONG)_code);
```

That has two source-level boundary gaps:

- allocation failure writes through `_code == NULL`;
- the freshly generated executable stub is published without an instruction
  cache coherency boundary.

Official references:

- https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-flushinstructioncache
- https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualprotect
- https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc

## Data

`Dll_FixWow64Syscall`, `_code`, `Dll_AllocCode128`, `X86SwitchTo64BitMode`,
13-byte WOW64 transition stub, `__writefsdword(0xC0, ...)`,
`FlushInstructionCache`, `Dll_IsWow64`, `Dll_Windows`, pre-Windows 10 WOW64
thunk selection, and thread-specific `fs:[0xC0]` publication.

## Schema

`DLLHOOK_WOW64_STUB_PUBLISH_GATE` says:

- `Dll_FixWow64Syscall` owns the pre-Windows 10 WOW64 transition stub before it
  is published into `fs:[0xC0]`.
- `Dll_AllocCode128` may fail and must be gated before any stub byte write.
- The generated stub is executable code and must be flushed before publication.
- `__writefsdword(0xC0, ...)` is the publication edge for the current thread.
- The patch must not change the generated byte sequence, Windows 10
  `wow64cpu` dispatcher hook path, NoSysCallHooks policy, or per-thread call
  topology.

## Topology

Legal pre-Windows 10 path:

```text
Dll_IsWow64 && Dll_Windows < 10
  -> read original fs:[0xC0] X86SwitchTo64BitMode
  -> allocate executable 128-byte code slot
  -> gate allocation success
  -> write 13-byte transition stub
  -> FlushInstructionCache(stub, 13)
  -> publish stub pointer into fs:[0xC0]
```

## Logic Risk

The WOW64 transition slot is a thread-local executable dispatch pointer. Writing
through a failed allocation is an immediate null dereference. Publishing a
freshly generated executable stub without a cache-coherency boundary can let the
thread transition path observe stale or partially coherent instructions after
Sandboxie reports the hook installed.

This SREV does not redesign WOW64 thunk selection. It only gates the local
allocation and executable-code publication edge.

## Fix

`Dll_FixWow64Syscall` now returns if `Dll_AllocCode128` fails. After writing the
13-byte pre-Windows 10 WOW64 transition stub, it calls
`FlushInstructionCache(GetCurrentProcess(), _code, 13)` before publishing `_code`
through `__writefsdword(0xC0, ...)`. The source comment now points at this SREV
as the owner of the 13-byte stub layout.

## Acceptance Gate

`docs/plan/check-srev-247.py` validates the draft-07 schema, official reference
links, source allocation gate before the first `_code` write, instruction-cache
flush before `__writefsdword`, preservation of the generated byte sequence,
source comment ownership of the generated byte sequence, preservation of the
Windows 10 path, and the ledger fragment.

Runtime/build gate: Windows 32-bit process under WOW64 on a pre-Windows 10
target or controlled compatibility VM proving the stub still routes syscalls
through the intended thunk, plus allocation-failure injection proving the path
returns without writing through NULL.
