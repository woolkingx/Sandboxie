### SREV-129: NetApi UseAdd Auth Identity Length Gate

| Field | Content |
|---|---|
| Severity | [major] |
| Status | patched source-level after official NetUseAdd / USE_INFO data-shape review; needs Windows NetUseAdd broker runtime proof |
| Evidence | `Sandboxie/core/svc/netapiserver.cpp` was the highest-ranked unnamed reviewable core file after SREV-128. `Sandboxie/core/svc/netapiwire.h` defines `NETAPI_USE_ADD_REQ` as a fixed wire packet with `ui4_auth_identity[2048+2]`, and `Sandboxie/core/dll/netapi.c` constructs that request from client `USE_INFO_*` input. `NetApiServer::UseAdd` receives the packet, converts local fields into a `USE_INFO_*` view, impersonates the caller, calls `NetUseAdd(NULL, req->level, (UCHAR *)&info, &parm_index)`, then starts `LaunchSlave` only on success. The string length validators set `parm_index` and stop before impersonation, but the old `ui4_auth_identity_length > 2048` branch only set `error_code = ERROR_INVALID_PARAMETER` and continued. The later impersonation and `NetUseAdd` call overwrote `error_code` and consumed a partially initialized local `USE_INFO_4`. Microsoft documents `NetUseAdd` as receiving a `buf` whose format depends on Level, and documents `ERROR_INVALID_PARAMETER` / `parm_err` as the invalid `USE_INFO_*` member signal. Microsoft documents `USE_INFO_2` string pointer members and `USE_INFO_3` as nesting `USE_INFO_2` plus `ui3_flags`; the local level-4 extension follows the same validated-wire-to-pointer-view topology. |
| Data | `NetApiServer::UseAdd`, `NETAPI_USE_ADD_REQ`, `NETAPI_USE_ADD_RPL`, `req->level`, `ui4_auth_identity_length`, `ui4_auth_identity[2048+2]`, local `USE_INFO_4`, `error_code`, `parm_index`, `PipeServer::ImpersonateCaller`, `NetUseAdd`, `LaunchSlave`, and client-side `NetApi_NetUseAdd`. |
| Schema | `NETAPI_USEADD_AUTH_IDENTITY_LENGTH_GATE` says `UseAdd` validates every `NETAPI_USE_ADD_REQ` wire field before `PipeServer::ImpersonateCaller` or `NetUseAdd` can run; `ui4_auth_identity_length` uses the fixed 2048 byte wire buffer limit; `ULONG -1` remains the null auth identity sentinel; values greater than 2048 set `ERROR_INVALID_PARAMETER` and exit before impersonation; valid auth identity bytes are locally terminated before `USE_INFO_4` points at the wire buffer; `parm_index` based string length failures still return `ERROR_INVALID_PARAMETER` before impersonation; `NetUseAdd` receives only a `USE_INFO` shaped buffer assembled from validated local wire fields; `LaunchSlave` still runs only after `NetUseAdd` succeeds; NetUseAdd level policy, local string limits, password handling, and drive notification topology are unchanged. |
| Topology | Legal flow is fixed `NETAPI_USE_ADD_REQ`, validate `h.length` and `level`, validate/cap local, remote, password, username, domain, and auth identity fields, assemble a local `USE_INFO_*` pointer view into the fixed wire buffers, impersonate caller, call `NetUseAdd`, return `NETAPI_USE_ADD_RPL`, and optionally run `LaunchSlave` only when `NetUseAdd` succeeds. Invalid `ui4_auth_identity_length > 2048` now flows directly to the reply path before impersonation and before `NetUseAdd`. |
| Logic Risk | The old code confused setting an error value with owning the transition. Since `error_code` was overwritten later, an impossible wire length could still cross into the privileged service broker and native NetAPI call. Because the valid branch also initializes the local `USE_INFO_4` pointer and length fields, skipping that branch left the level-4 view outside a legal state. The correct local repair is a validation barrier before impersonation, not a policy change to NetUseAdd levels or drive notification. |
| Official Shape | `docs/plan/srev-129-netapi-useadd-auth-identity-length-gate.md` records Microsoft `NetUseAdd`, `USE_INFO_2`, and `USE_INFO_3` references. `docs/plan/srev-129-netapi-useadd-auth-identity-length-gate.schema.json` records the JSON Schema draft-07 local `NETAPI_USEADD_AUTH_IDENTITY_LENGTH_GATE` contract. |
| Fix | `NetApiServer::UseAdd` now checks `if (error_code) goto finish;` after level-4 field validation and before the existing `parm_index` gate. Invalid `ui4_auth_identity_length > 2048` therefore returns `ERROR_INVALID_PARAMETER` without impersonating the caller or calling `NetUseAdd`. Valid auth identity data, `ULONG -1` null sentinel behavior, existing string length parameter errors, `NetUseAdd` call shape, reply shape, and success-only `LaunchSlave` behavior are unchanged. |
| Acceptance Gate | `docs/plan/check-srev-129.py` validates the draft-07 schema, official references, wire shape, client request construction precedent, invalid auth identity length gate before impersonation, existing `parm_index` gate preservation, valid auth identity termination and pointer assignment, `NetUseAdd` call topology, success-only `LaunchSlave`, stale ungated pattern removal, and ledger entry; `docs/plan/check-srev-129.sh` is the matrix wrapper. Runtime/build gate: Windows service build for `netapiserver.cpp`, valid `NetUseAdd` mapping smoke, malformed level-4 request with `ui4_auth_identity_length = 2049` proving no `NetUseAdd` call and `ERROR_INVALID_PARAMETER`, null sentinel request proving unchanged behavior, and 2048-byte valid auth identity request proving unchanged forwarding. |
