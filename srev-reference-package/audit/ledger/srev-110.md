### SREV-110: Thread Impersonation Offset Boundary

| Field | Content |
|---|---|
| Severity | [major] |
| Status | source-level classified after official `PsImpersonateClient`, `PsReferenceImpersonationToken`, `PsRevertToSelf`, impersonation-level, and `SeImpersonatePrivilege` policy shape; comment-only source clarification, no behavior change |
| Evidence | `Sandboxie/core/drv/thread.c` is the top-ranked unnamed reviewable core file after uncovered comment risks reached zero. Its highest-risk path captures an active thread impersonation token with `PsReferenceImpersonationToken`, stores it in `THREAD::token_object`, and later replays it during syscall dispatch through `Thread_MyImpersonateClient`. Microsoft documents that `PsImpersonateClient` may limit impersonation when token SID/restriction conditions are not met, warns that raising an untrusted user thread's privilege state is extremely unsafe, and documents `SecurityIdentification` as identity-only while `SecurityImpersonation` can impersonate locally. Local source intentionally calls `PsImpersonateClient` at `SecurityIdentification`, then updates the private `ETHREAD` client-security field using `Dyndata_Config.ImpersonationData_offset` after verifying the field still points at `TokenObject`; mismatch fails with `STATUS_ACCESS_DENIED` and logs `MSG_1222`/`0x62`. |
| Data | `Thread_SetThreadToken`, `Thread_StoreThreadToken`, `Thread_MyImpersonateClient`, `Thread_ClearThreadToken`, `PsReferenceImpersonationToken`, `PsImpersonateClient`, `PsGetCurrentThread`, `PsImpersonateClient(..., NULL, ...)`, `THREAD::token_object`, `token_CopyOnOpen`, `token_EffectiveOnly`, `token_ImpersonationLevel`, `Dyndata_Config.ImpersonationData_offset`, XP `PS_IMPERSONATION_INFORMATION`, Vista+ packed client-security pointer/level bits, `STATUS_ACCESS_DENIED`, `STATUS_UNKNOWN_REVISION`, `MSG_1222`, and `Process_SetTerminated`. |
| Schema | `THREAD_IMPERSONATION_OFFSET_BOUNDARY` says `Thread_StoreThreadToken` references the active impersonation token before storage; stored thread tokens keep `CopyOnOpen`, `EffectiveOnly`, and local `SecurityImpersonation` replay level; `Thread_SetThreadToken` replays a stored thread token or process primary token for syscall dispatch; `Thread_MyImpersonateClient` calls `PsImpersonateClient` at `SecurityIdentification` first; the `ETHREAD` client-security field update is private dynamic-data owned state; Vista+ validates the masked client-security pointer against `TokenObject` before writing level bits; XP validates `PS_IMPERSONATION_INFORMATION.TokenObject` before writing `ImpersonationLevel`; offset mismatch returns `STATUS_ACCESS_DENIED` and logs `MSG_1222`/`0x62`; this source-local SREV must not replace the shim with direct `SecurityImpersonation` or worker-thread dispatch. |
| Topology | Capture path: `PsReferenceImpersonationToken(PsGetCurrentThread)` returns a referenced token plus `CopyOnOpen`, `EffectiveOnly`, and level; under `proc->threads_lock`, Sandboxie stores the token and flags in the thread map and dereferences the replaced token after lock release. Replay path: `Thread_SetThreadToken` reads the stored token under `proc->threads_lock`, references it if present, otherwise uses `proc->primary_token`, calls `Thread_MyImpersonateClient`, and dereferences the transient stored-token reference. Private offset path: `Thread_MyImpersonateClient` calls `PsImpersonateClient(..., SecurityIdentification)`, gets `Dyndata_Config.ImpersonationData_offset`, verifies the XP or Vista+ client-security field points to `TokenObject`, writes only the impersonation level field/bits, and fails closed on mismatch. |
| Logic Risk | This is a compatibility shim, not a public DDI contract. A direct `PsImpersonateClient(..., SecurityImpersonation)` replacement would likely restore the official downgrade behavior that prevents Sandboxie syscalls from running under the original token context. A worker-thread replacement may be architecturally cleaner for privileged work, but it would cross syscall dispatch, token replay, and object filtering ownership. The source-local invariant is therefore fail-closed private-offset verification, not pretending the private offset is generally safe. |
| Official Shape | `docs/plan/srev-110-thread-impersonation-offset-boundary.md` records Microsoft `PsImpersonateClient`, `PsReferenceImpersonationToken`, `PsRevertToSelf`, `SECURITY_IMPERSONATION_LEVEL`, and `SeImpersonatePrivilege` references. `docs/plan/srev-110-thread-impersonation-offset-boundary.schema.json` records the JSON Schema draft-07 local `THREAD_IMPERSONATION_OFFSET_BOUNDARY` contract. |
| Fix | Comment-only source clarification: the old workaround wording now identifies the path as a Sandboxie compatibility shim, states that the supported API can downgrade the sandboxed caller to `SecurityIdentification`, names the dynamic-data-owned `ETHREAD` client-security update, and states that unverifiable offsets fail closed. No token capture, reference counting, impersonation call, private offset, failure status, process termination, object access filter, or syscall behavior changed. |
| Acceptance Gate | `docs/plan/check-srev-110.py` validates the draft-07 schema, official references, token capture/replay topology, private offset verification for XP and Vista+ paths, failure status/logging, source comment clarification, absence of a direct `SecurityImpersonation` `PsImpersonateClient` replacement, and ledger entry; `docs/plan/check-srev-110.sh` is the matrix wrapper. Runtime gate: Windows matrix over each supported build dynamic-data offset, thread token capture through `NtImpersonateAnonymousToken` / `NtImpersonateClientOfPort`, syscall dispatch requiring original token context, offset mismatch fail-closed observation, Driver Verifier, HVCI where supported, and object access filter behavior before and after `Thread_SetThreadToken`. |
