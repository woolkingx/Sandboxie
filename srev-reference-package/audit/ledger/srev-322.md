### SREV-322: Proc WerFault Dump Suppression Boundary

| Field | Content |
|---|---|
| Severity | [major] |
| Status | patched source-level duplicate WerFault handle lifetime; needs Windows WER LocalDumps runtime proof |
| Evidence | `Proc_CreateProcessInternalW` resumes most newly created suspended child processes after token fixup. For `WerFault.exe`, it resumes the first observed WerFault process, logs 2224, records `g_boolWasWerFaultLastProcess = TRUE`, and waits 30000 ms for WER/LocalDumps capture. For later WerFault processes, it calls `TerminateProcess` and waits on the process handle. The old duplicate path closed the returned process/thread handles while the surrounding logic remained on an `ok` create path; the source now removes that premature handle close and keeps `PROCESS_INFORMATION` handles caller-owned. |
| Data | `Proc_CreateProcessInternalW`, `resume_thread`, `lpApplicationName`, `WerFault.exe`, `g_boolWasWerFaultLastProcess`, `lpProcessInformation->hProcess`, `lpProcessInformation->hThread`, `ResumeThread`, `TerminateProcess`, `WaitForSingleObject`, `CloseHandle`, `SbieApi_Log(2224)`, and `Dump_Init` / `EnableMiniDump` adjacency. |
| Schema | `PROC_WERFAULT_DUMP_SUPPRESSION_BOUNDARY` says WerFault dump suppression is local `proc.c` process-lifetime policy; WER dump configuration and in-process minidump writing are separate owners; the first WerFault process may be resumed and waited for dump capture; repeated WerFault processes may be terminated only after the exact WerFault predicate and duplicate-state gate; duplicate WerFault suppression terminates and waits but keeps `PROCESS_INFORMATION` handles caller-owned on the successful create path; the runtime matrix must prove LocalDumps setup, WerFault launch count, dump file output, duplicate suppression, output handle behavior, negative controls, and `EnableMiniDump` regression; LocalDumps capture timing, duplicate WerFault lifetime, and caller-visible process/thread handle semantics must be proven before release; SREV-322 source path removes duplicate-path premature handle close while preserving first WerFault and non-WerFault resume behavior. |
| Topology | `created suspended child process -> token fixup -> resume_thread gate -> WerFault predicate -> first WerFault: ResumeThread -> wait for dump capture -> repeated WerFault: TerminateProcess -> WaitForSingleObject -> return signaled handles caller-owned -> non-WerFault: ResumeThread`. Adjacent dump topology remains `dllmain.c EnableMiniDump -> Dump_Init -> MiniDumpWriteDump (SREV-156/SREV-237)` and `Windows Error Reporting -> LocalDumps registry -> WerFault dump capture`. |
| Logic Risk | Generic design-flaw wording hides an active process-lifetime and output-handle boundary. The repeated-WerFault path used to close process/thread handles while the caller-facing create path remained successful. That made the duplicate process handle no longer caller-visible even though the API surface returned success. The source now removes the premature handle close while preserving duplicate termination and wait behavior; Windows crash/WER runtime proof remains required before release. |
| Official Shape | `docs/plan/srev-322-proc-werfault-dump-suppression-boundary.md` records Microsoft WER, LocalDumps, `ResumeThread`, `TerminateProcess`, `WaitForSingleObject`, and `CloseHandle` references. `docs/plan/srev-322-proc-werfault-dump-suppression-boundary.schema.json` records the JSON Schema draft-07 local `PROC_WERFAULT_DUMP_SUPPRESSION_BOUNDARY` contract. |
| LocalDumps Matrix | Supported Windows 10/11 builds; global/per-app `LocalDumps`; `DumpFolder`, `DumpCount`, `DumpType`, `CustomDumpFlags`, ACL, WER-disabled, automatic-debugging, and missing-registry-key states; `EnableMiniDump` on/off; default/restricted/blocked-write boxes; deterministic native crash, repeated crash, custom crash reporter, and non-crashing child; first/duplicate WerFault process ids, `SbieApi_Log(2224)`, `ResumeThread`, `TerminateProcess`, wait results, exit code; dump path/count/timestamps/type/process identity/replacement/no-dump states; first/duplicate/non-WerFault/failure-path process/thread handle validity and caller `GetExitCodeProcess` / `WaitForSingleObject` / `CloseHandle` readback; SREV-156/SREV-237 in-process dump adjacency; and negative controls for exact predicate, WER disabled, automatic debugging, ACL denial, and fresh-box first WerFault. |
| Shared Runtime Capture Evidence | Runtime records use `docs/plan/srev-092-322-user-lifecycle-runtime-capture.schema.json` with feature path `werfault-localdumps-boundary`; `docs/plan/srev-092-322-user-lifecycle-runtime-capture-playbook.md` is the capture procedure; `docs/plan/check-srev-092-322-user-lifecycle-runtime-capture.sh` validates the shared user-mode lifecycle evidence contract. |
| Fix | Source-level local lifetime fix. The source now names the SREV-322 boundary: first WerFault is resumed for WER/LocalDumps capture and later ones are terminated only after the exact duplicate gate. The duplicate path no longer calls `CloseHandle` on the caller-facing `PROCESS_INFORMATION` process/thread handles while returning through the successful create path. No predicate, duplicate-state flag, `ResumeThread`, `TerminateProcess`, `WaitForSingleObject`, logging, return value, or output handle writeback behavior changed. |
