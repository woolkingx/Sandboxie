# SREV-173: Hook Trampoline Code Capacity

## Stage Gate

```text
stage: schema -> boundary -> topology -> logic -> action -> verify
input artifact: Sandboxie/core/dll/hook_inst.c, Sandboxie/core/dll/hook_tramp.c, Sandboxie/core/dll/hook.h, Sandboxie/core/drv/hook.c, Intel instruction encoding reference, Microsoft ProbeForWrite reference
output artifact: trampoline emission checks the bounded HOOK_TRAMP.code storage before writing relocated or expanded instruction bytes
owner: Sandboxie/core/dll/hook_tramp.c
acceptance gate: docs/plan/check-srev-173.py and docs/plan/check-srev-173.sh
```

## Data

`hook_inst.c` analyzes one IA-32 / Intel 64 instruction and reports its source
length and relocation shape through `HOOK_INST`. `hook_tramp.c` consumes that
shape in `Hook_Tramp_Copy` and emits relocated bytes into `HOOK_TRAMP.code`.

The local storage shape is bounded:

- `HOOK_TRAMP.code` is a 64-byte code buffer in `Sandboxie/core/dll/hook.h`.
- `Hook_Api_Tramp` probes a caller-supplied 96-byte trampoline buffer with
  16-byte alignment before calling `Hook_BuildTramp`.
- `Hook_Tramp_CountBytes` counts source instruction bytes only until the source
  detour span reaches 5 bytes on x86 or 12 bytes on x64.
- `Hook_Tramp_Copy` may expand one source instruction into a larger emitted
  sequence: x64 conditional jumps can become 16 bytes, short jumps can become
  14 bytes, direct call/jump can become 16 bytes, and RIP-relative memory
  access can add a 10-byte `mov rax, addr` prefix plus optional `push/pop rax`.
- The final jump-back stub also consumes trampoline code bytes.

Before this SREV, `Hook_Tramp_Copy` wrote relocated bytes and the final jump-back
stub without proving that the expanded emission plus reserved final stub fit
inside `HOOK_TRAMP.code`.

## Official Shape

- Intel's official Intel 64 and IA-32 Software Developer's Manuals are the
  instruction-set source for IA-32 and Intel 64 variable-length instruction
  encodings and control-transfer instruction forms:
  `https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html`.
- Microsoft documents `ProbeForWrite` as validating a user-mode buffer range and
  alignment, but also states that subsequent driver accesses must still be
  protected because user-mode address protection can change at any time:
  `https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-probeforwrite`.

The official instruction set defines source instruction shape. It does not make
Sandboxie's relocated trampoline emission fit automatically. The local owner
must prove that every generated byte sequence stays inside the local trampoline
code buffer.

## Schema

`HOOK_TRAMP_CODE_CAPACITY` says:

- `hook_inst.c` owns source instruction analysis only; it does not own the
  destination trampoline buffer.
- `hook_tramp.c` owns trampoline code emission and must bound-check the emitted
  instruction sequence against `HOOK_TRAMP.code`.
- `Hook_Tramp_EmitLength` names the destination byte count for each local
  relocation shape before `Hook_Tramp_Copy` writes bytes.
- `Hook_Tramp_HasCodeSpace` must prove both the current emitted sequence and the
  reserved final jump-back stub fit inside `HOOK_TRAMP.code`.
- `Hook_Tramp_Copy` fails closed when an analyzed source sequence would overflow
  the trampoline code buffer.
- This SREV does not change instruction decoding, source byte counting,
  relocation semantics, allocation, page protection, or instruction-cache
  ownership.

## Topology

Legal trampoline emission topology:

```text
Hook_Analyze source instruction
  -> HOOK_INST source length and relocation kind
  -> Hook_Tramp_EmitLength destination byte count
  -> Hook_Tramp_HasCodeSpace(current emission, final jump-back reserve)
  -> write relocated bytes only if the bounded code buffer can hold them
  -> before final stub, Hook_Tramp_HasCodeSpace(final stub)
  -> publish trampoline size
```

## Logic Risk

`Hook_Tramp_CountBytes` reasons about source bytes, but `Hook_Tramp_Copy` writes
destination bytes. Those are not the same shape after relocation. A compact x64
source prologue with multiple short branches or RIP-relative instructions can
require more destination bytes than the original source span. Without a
destination-capacity gate, `Hook_Tramp_Copy` can write past `HOOK_TRAMP.code`
and corrupt adjacent trampoline metadata or memory while still returning a
usable-looking trampoline pointer.

The minimal repair is not to redesign the instruction analyzer. The repair is to
make the destination owner name and enforce its own capacity before every
emission and before the final jump-back stub.

## Action

`hook_tramp.c` now adds:

- `Hook_Tramp_HasCodeSpace` for bounded writes inside `HOOK_TRAMP.code`.
- `Hook_Tramp_JumpBackSize` for the final x86/x64 jump-back reserve.
- `Hook_Tramp_EmitLength` for local relocation expansion sizes.

`Hook_Tramp_Copy` now checks the computed emitted length plus reserved final
jump-back space before copying or expanding the current instruction, and checks
the final stub space before writing it.
