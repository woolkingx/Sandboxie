### SREV-159: PipeServer Thread Vector Lifetime

| Field | Content |
|---|---|
| Severity | [major] |
| Status | patched source-level after official `HeapAlloc`, `CreateThread`, `WaitForMultipleObjects`, `CloseHandle`, and `HeapFree` shape review; needs Windows SbieSvc startup/shutdown runtime proof |
| Evidence | `Sandboxie/core/svc/PipeServer.h` was the highest-ranked unnamed reviewable core file after SREV-158. It declares the SbieSvc `PipeServer` owner for LPC server lifecycle, target registration, caller identity helpers, impersonation, server port handle, and worker thread handles. `Sandboxie/core/svc/PipeServer.cpp` allocates `m_Threads` with `HeapAlloc`, creates worker threads in `Start`, and waits on them in the destructor. Before this SREV, `HeapAlloc` failure was only logged while `Start` still indexed `m_Threads[i]`; partial `CreateThread` failure returned `false` while leaving the port and already-created workers alive; the destructor waited on `NUMBER_OF_THREADS` entries whenever `m_Threads` was non-null, even if startup was partial or never reached thread creation; and thread handles plus the heap vector were not closed/freed. Microsoft documents `HeapAlloc` as returning `NULL` on failure without `HEAP_GENERATE_EXCEPTIONS`; `CreateThread` as returning `NULL` on failure and leaving a thread object alive until thread termination and all handles are closed; `WaitForMultipleObjects` as waiting on a counted handle array; `CloseHandle` as closing thread handles; and `HeapFree` as freeing `HeapAlloc` memory. |
| Data | `Sandboxie/core/svc/PipeServer.h`, `Sandboxie/core/svc/PipeServer.cpp`, `PipeServer::PipeServer`, `PipeServer::Start`, `PipeServer::~PipeServer`, `PipeServer::ShutdownPortAndThreads`, `m_hServerPort`, `m_Threads`, `m_ThreadCount`, `NUMBER_OF_THREADS`, `HeapAlloc`, `HeapFree`, `CreateThread`, `WaitForMultipleObjects`, `TerminateThread`, `CloseHandle`, `NtRequestPort`, `NtClose`, and `InitializePipe`. |
| Schema | `PIPESERVER_THREAD_VECTOR_LIFETIME` says `PipeServer` owns a thread handle vector allocated from `GetProcessHeap`; `Start` must not create the server port or index `m_Threads` when vector allocation failed; `m_ThreadCount` is the number of valid thread handles currently stored at the front of `m_Threads`; waits, termination, close, and cleanup may operate only on `m_ThreadCount` valid handles; every successful `CreateThread` handle is eventually closed with `CloseHandle`; startup failure after partial thread creation shuts down the published port, wakes existing worker threads, closes their handles, preserves the `CreateThread` `GetLastError` value, and returns `false`; the `HeapAlloc` vector is freed with `HeapFree` in the destructor; and this SREV does not change LPC message framing, request dispatch, target registration, impersonation, or server-port security descriptor policy. |
| Topology | Legal startup flow is constructor, `HeapAlloc` thread vector, `Start`, vector-allocation gate, security descriptor, `NtCreatePort`, `CreateThread` loop, and success only after `m_Threads[0..m_ThreadCount)` contains all `NUMBER_OF_THREADS` handles. Legal failure/shutdown flow is `m_hServerPort` exchange to `NULL`, wake worker threads through the old port handle, wait only on counted handles, terminate counted handles on timeout, close counted handles, close the old port handle, and destructor `HeapFree` for the thread vector. |
| Logic Risk | The vector pointer was capacity storage, not proof of valid handles. Using it as a full handle array could dereference `NULL`, wait on invalid handles, or leave a reachable SbieSvc port and worker threads after service startup had already reported failure. This is a local lifecycle defect; the fix must not alter LPC payload parsing or impersonation policy. |
| Official Shape | `docs/plan/srev-159-pipeserver-thread-vector-lifetime.md` records Microsoft `HeapAlloc`, `CreateThread`, `WaitForMultipleObjects`, `CloseHandle`, and `HeapFree` references. `docs/plan/srev-159-pipeserver-thread-vector-lifetime.schema.json` records the JSON Schema draft-07 local `PIPESERVER_THREAD_VECTOR_LIFETIME` contract. |
| Fix | `PipeServer` now tracks `m_ThreadCount`, gates `Start` before port creation when `m_Threads` allocation failed, and increments the count only after `CreateThread` succeeds. `ShutdownPortAndThreads` centralizes teardown for destructor and partial startup failure: it withdraws `m_hServerPort`, wakes workers, waits on counted handles, terminates counted handles on timeout, closes counted handles, resets the count, and closes the old port handle. The destructor now calls this helper and frees the thread vector with `HeapFree`. |
| Acceptance Gate | `docs/plan/check-srev-159.py` validates the draft-07 schema, official references, `PipeServer.h` lifecycle state, constructor count initialization, `Start` allocation gate before port creation, partial `CreateThread` cleanup with preserved error, counted wait/terminate/close topology, stale full-vector destructor wait removal, `HeapFree` of the vector, and ledger entry; `docs/plan/check-srev-159.sh` is the matrix wrapper. Runtime/build gate: Windows SbieSvc build, forced `HeapAlloc` failure proving `Start` returns `ERROR_NOT_ENOUGH_MEMORY` before publishing the port, forced mid-loop `CreateThread` failure proving already-created workers exit and handles are closed, ordinary startup/shutdown smoke proving all worker handles close, and normal LPC request dispatch smoke. |
