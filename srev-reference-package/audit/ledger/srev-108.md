### SREV-108: EpMapper Dynamic Port Scope And Binding Lifetime

| Field | Content |
|---|---|
| Severity | [major] |
| Status | patched source-level after official RPC endpoint mapper, RPC binding lifetime, SCM service-process, and public ALPC event/debugger shape; needs Windows RPC/ALPC dynamic-port runtime proof |
| Evidence | `Sandboxie/core/svc/EpMapperServer.cpp` resolves sandboxed dynamic RPC endpoints by configured service name or configured RPC interface id, then calls `API_OPEN_DYNAMIC_PORT` with process id `0` so the driver opens the endpoint through its global dynamic-port list. The uncovered comments proposed per-sandbox or per-process filtering, but the current `API_OPEN_DYNAMIC_PORT_ARGS` schema in `Sandboxie/core/drv/api_defs.h` only carries `port_name`, `process_id`, `port_id`, `filter_num`, and `filter_ids`; no box/sandbox scoped key exists. During official-shape review, Microsoft `RpcMgmtEpEltInqNextW` documentation showed a concrete source bug: a returned `Binding` handle is allocated by the RPC runtime and must be released with `RpcBindingFree`. The old loop converted each binding to a string and freed the string, but did not free the binding handle. |
| Data | `EpMapperServer::EpmapperGetPortNameHandler`, `PipeServer::GetCallerProcessId`, `SbieApi_QueryProcess`, `RpcPortBindingIfId`, `RpcPortBindingSvc`, `OpenSCManager`, `OpenService`, `QueryServiceStatusEx`, `SERVICE_STATUS_PROCESS.dwProcessId`, `API_GET_DYNAMIC_PORT_FROM_PID`, `RpcMgmtEpEltInqBegin`, `RpcMgmtEpEltInqNextW`, `RpcBindingToStringBindingW`, `RpcStringFreeW`, `RpcBindingFree`, `RpcMgmtEpEltInqDone`, `RpcPortFilter`, `API_OPEN_DYNAMIC_PORT`, `Ipc_Api_OpenDynamicPort`, `Ipc_CreateDynamicPort`, `Ipc_CheckPortRequest_Dynamic`, `Ipc_GetRpcMsgId`, and `IPC_DYNAMIC_PORT.FilterIDs`. |
| Schema | `EPMAPPER_DYNAMIC_PORT_SCOPE_AND_BINDING_LIFETIME` says the caller process id maps to a sandbox box before policy lookup; `RpcPortBindingIfId` resolves through local RPC endpoint mapper inquiry; `RpcPortBindingSvc` resolves through SCM service process id and driver ALPC owner lookup; each successful `RpcMgmtEpEltInqNextW` binding handle is freed with `RpcBindingFree`; `RpcBindingToStringBindingW` output is freed with `RpcStringFreeW`; `RpcMgmtEpEltInqDone` deletes the inquiry context; `API_OPEN_DYNAMIC_PORT` currently carries process-id or global scope only; process id `0` is the existing global dynamic-port compatibility path; `RpcPortFilter` message ids are attached to the driver dynamic-port entry; per-sandbox dynamic ports require a driver/API schema extension with a scoped key; per-process or per-sandbox ALPC message filtering must not be pretended in service-only code. |
| Topology | Caller pid -> `SbieApi_QueryProcess` -> box name -> endpoint id. Service-name endpoints flow through SCM `QueryServiceStatusEx(SC_STATUS_PROCESS_INFO)` and driver `API_GET_DYNAMIC_PORT_FROM_PID`. Interface-id endpoints flow through `RpcMgmtEpEltInqBegin` / `RpcMgmtEpEltInqNextW` / `RpcBindingToStringBindingW` / `RpcStringFreeW` / `RpcBindingFree` / `RpcMgmtEpEltInqDone`. Successful resolution loads `RpcPortFilter` config and calls `API_OPEN_DYNAMIC_PORT(port, 0, port_id, filter_count, filter_ids)`. The driver stores `IPC_DYNAMIC_PORT` entries in the global `Ipc_Dynamic_Ports` list keyed by port id/name, optionally adds a per-process open path when `process_id != 0`, and applies filter ids when `Ipc_CheckPortRequest_Dynamic` matches a dynamic-port entry and parses the local RPC message id. |
| Logic Risk | Changing the service call from process id `0` to the resolving process id would break the existing cross-process compatibility case noted by the source comment: one sandboxed process may resolve a dynamic endpoint and another may use it. Keeping process id `0` preserves behavior, but the old TODO wording hid the real missing shape: a scoped dynamic-port key in the driver/API contract. Separately, repeated endpoint inquiries leaked RPC binding handles because the RPC runtime owns each `Binding` returned by `RpcMgmtEpEltInqNextW`. |
| Official Shape | `docs/plan/srev-108-epmapper-dynamic-port-scope-and-binding-lifetime.md` records Microsoft `RpcMgmtEpEltInqBegin`, `RpcMgmtEpEltInqNextW`, `RpcMgmtEpEltInqDone`, `RpcBindingToStringBindingW`, `RpcBindingFree`, `RpcStringFreeW`, `QueryServiceStatusEx`, `SERVICE_STATUS_PROCESS`, ALPC ETW, and LPC/ALPC debugger references. `docs/plan/srev-108-epmapper-dynamic-port-scope-and-binding-lifetime.schema.json` records the JSON Schema draft-07 local `EPMAPPER_DYNAMIC_PORT_SCOPE_AND_BINDING_LIFETIME` contract. |
| Fix | The interface-id endpoint inquiry loop now frees every successfully returned binding handle with `RpcBindingFree` after string conversion and string cleanup, while preserving the first accepted `LRPC-*` endpoint behavior and `RpcMgmtEpEltInqDone` cleanup. The stale per-sandbox/per-process TODO comments were replaced with a source comment naming the actual API/schema boundary. No endpoint config parsing, SCM lookup, global process-id `0` compatibility path, driver dynamic-port list, or message-id filter policy changed. |
| Acceptance Gate | `docs/plan/check-srev-108.py` validates the draft-07 schema, official references, endpoint mapper inquiry topology, RPC binding/string/inquiry lifetime calls, stale TODO removal, preservation of process id `0` global compatibility, driver API schema evidence that no sandbox key exists, dynamic-port filter topology, and ledger entry; `docs/plan/check-srev-108.sh` is the matrix wrapper. Runtime gate: Windows matrix with configured `RpcPortBindingIfId`, configured `RpcPortBindingSvc`, Chrome/Game Config Store style cross-process endpoint use, `RpcPortFilter` allow/deny observations, repeated endpoint lookup under service memory/resource tracing, sandboxed same-box cross-process access, different-box negative case after any future scoped schema change, and ALPC ETW / debugger observation for the actual local-RPC send/receive path. |
