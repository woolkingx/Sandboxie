### SREV-123: SCM Create Request Allocation Lifetime

| Field | Content |
|---|---|
| Severity | [major] |
| Status | patched source-level after official Win32 heap-allocation and SCM create/start shape; needs Windows service-runtime build/fault-injection proof |
| Evidence | `Sandboxie/core/dll/scm_create.c` was the highest-ranked unnamed reviewable core file after SREV-122. `Scm_AddBoxedService` allocated `names2` with `Dll_AllocTemp` and immediately copied the existing `SandboxedServices` `REG_MULTI_SZ` into it. `Scm_CreateServiceW` allocated the fake `SC_HANDLE` service-name buffer with `Dll_Alloc` and immediately wrote the `tzuk` marker and service name into it after creating the service key and adding the service to `SandboxedServices`. `Scm_StartBoxedService2` allocated a `SERVICE_RUN_REQ` with `Dll_Alloc`, immediately wrote request fields into it, and did not free that request buffer after `SbieDll_CallServer` returned. The local `Dll_AllocFromPool` may return `NULL` before the sandbox name is initialized, and its allocation shape is compatible with the official Win32 heap-allocation failure shape. |
| Data | `Scm_AddBoxedService`, `Scm_CreateServiceW`, `Scm_StartBoxedService2`, `Dll_AllocTemp`, `Dll_Alloc`, `Dll_Free`, `Scm_GetBoxedServices`, `SandboxedServices`, `REG_MULTI_SZ`, fake `SC_HANDLE` service-name buffer, `SERVICE_RUN_REQ`, `SbieDll_CallServer`, `ERROR_NOT_ENOUGH_MEMORY`, `STATUS_INSUFFICIENT_RESOURCES`, `NtSetValueKey`, `NtDeleteKey`, `NtClose`, and special-service heap path cleanup. |
| Schema | `SCM_CREATE_REQUEST_ALLOCATION_LIFETIME` says `Dll_Alloc` and `Dll_AllocTemp` may fail before returning writable storage; `Scm_AddBoxedService` writes `names2` only after `Dll_AllocTemp` succeeds; `Scm_CreateServiceW` writes the fake service-handle name only after `Dll_Alloc` succeeds; `Scm_CreateServiceW` allocates the fake service handle before `Scm_AddBoxedService` mutates `SandboxedServices`; `Scm_CreateServiceW` frees the fake service handle if `Scm_AddBoxedService` fails; `Scm_StartBoxedService2` fills `SERVICE_RUN_REQ` only after `Dll_Alloc` succeeds; `Scm_StartBoxedService2` frees `SERVICE_RUN_REQ` after `SbieDll_CallServer` returns; service creation policy, registry values, sandboxed-service list semantics, special service routing, and service-run wire shape are unchanged. |
| Topology | `Scm_AddBoxedService` flows from `Scm_GetBoxedServices()` to a newly allocated `names2` buffer, appends the requested service name, writes the `SandboxedServices` `REG_MULTI_SZ`, and frees `names2`. `Scm_CreateServiceW` creates and populates the service registry key, allocates and fills the fake `SC_HANDLE` payload, then mutates the boxed-service list; on later list failure it frees the fake handle buffer before deleting the partial service key. `Scm_StartBoxedService2` derives the service path, allocates `SERVICE_RUN_REQ + path`, fills `MSGID_SERVICE_RUN`, sends it through `SbieDll_CallServer`, frees the request, and returns the server Win32 status. |
| Logic Risk | The old allocation-free shape mixed persistent service creation with unchecked transient buffers. A null `names2` or fake-handle buffer could crash during service creation. Adding the service to `SandboxedServices` before proving the fake handle buffer existed could also leave registry/list state mutated without a handle to return. The service-run path had both a null-write risk and a normal-path request leak. The correct local fix is allocation and ownership gating at these data nodes, not a change to SCM access policy, service registry value semantics, special boxed-service routing, or server wire validation. |
| Official Shape | `docs/plan/srev-123-scm-create-request-allocation-lifetime.md` records Microsoft `HeapAlloc`, `HeapFree`, `CreateServiceW`, and `StartServiceW` references. `docs/plan/srev-123-scm-create-request-allocation-lifetime.schema.json` records the JSON Schema draft-07 local `SCM_CREATE_REQUEST_ALLOCATION_LIFETIME` contract. |
| Fix | `Scm_AddBoxedService` now checks `names2` after `Dll_AllocTemp` and returns `STATUS_INSUFFICIENT_RESOURCES` through the existing mutex/list cleanup path before writing the updated `REG_MULTI_SZ`. `Scm_CreateServiceW` now checks the fake service-handle name allocation before writing into it, performs that allocation before `Scm_AddBoxedService`, frees the handle-name buffer if the list update fails, and returns `ERROR_NOT_ENOUGH_MEMORY` on allocation failure. `Scm_StartBoxedService2` now checks the `SERVICE_RUN_REQ` allocation before filling it, frees any special-service heap path on allocation failure, and frees the request buffer after `SbieDll_CallServer` returns. No service creation policy, registry value shape, sandboxed-service list key, special service name routing, device map capture, request `msgid`, service run path copy, or call-server reply handling changed. |
| Acceptance Gate | `docs/plan/check-srev-123.py` validates the draft-07 schema, official references, local nullable `Dll_Alloc` / `Dll_AllocTemp` shape, `Scm_AddBoxedService` `names2` gate before writes, `Scm_CreateServiceW` fake-handle allocation before writes and before `Scm_AddBoxedService`, fake-handle cleanup on list-update failure, `Scm_StartBoxedService2` request allocation gate before writes, `SERVICE_RUN_REQ` cleanup after `SbieDll_CallServer`, stale unguarded allocation/write patterns removed, and ledger entry; `docs/plan/check-srev-123.sh` is the matrix wrapper. Runtime/build gate: Windows build for `scm_create.c`, allocation-failure injection for each patched allocation path, no stale `SandboxedServices` entry on fake-handle allocation failure, fake-handle cleanup on later list-update failure, request cleanup on service-run call-server return, and positive boxed-service create/start smoke proving unchanged registry values, list update, service-run request, and reply handling. |
