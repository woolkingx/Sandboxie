# SREV-002 Legacy Password SHA1 Hex Shape

Status: source-level spec before patch.

## Official Shape

Microsoft CryptoAPI documents `CryptCreateHash` as creating a hash object,
`CryptHashData` as adding bytes to that hash object, and `CryptGetHashParam`
with `HP_HASHVAL` as retrieving the binary hash value produced from those input
bytes. Microsoft also documents CryptoAPI as deprecated for new code and
recommends CNG for current cryptographic work.

The official API returns binary digest bytes. Printable hexadecimal encoding is
application-owned logic.

Sources:

- https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-cryptcreatehash
- https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-crypthashdata
- https://learn.microsoft.com/en-us/windows/desktop/api/wincrypt/nf-wincrypt-cryptgethashparam
- https://learn.microsoft.com/en-us/windows/win32/seccng/creating-a-hash-with-cng

## Local Shape

Sandboxie has two password formats:

- legacy: 40 hex WCHARs from SHA1 over at most 64 WCHARs of password
- current: 64 base64 WCHARs encoding `[16 byte salt][32 byte SHA256 hash]`

Current password writes use the SHA256/salt format. Legacy SHA1 remains only as
a read path for existing `EditPassword` values.

## Local Risk

The legacy byte-to-hex encoder shifted the high nibble by 8 instead of 4, making
the high hex digit always encode as `0`. Directly changing the shift would break
existing legacy `EditPassword` configs that were generated by the buggy encoder.

Leaving the bug implicit invites a future direct fix that silently locks users
out or a future comparison that only accepts the weakened legacy encoding.

## Patch Boundary

Keep legacy compatibility explicit and narrow:

- `HashPassword(..., LegacyBug = true)` preserves the old generated shape.
- 40-character legacy verification first checks the historical buggy shape.
- If that fails, it also checks canonical SHA1 hex with the correct high-nibble
  shift.
- New password writes continue using the SHA256/salt format.

This is not a full migration. Automatic rewrite from legacy SHA1 to SHA256 needs
a separate runtime gate because authorization currently should not mutate config
as a side effect.

## Acceptance Gate

- The old `>> 8` comment is gone.
- The legacy bug is represented as an explicit `LegacyBug` switch.
- 40-character legacy verification can accept both historical buggy and
  canonical SHA1 hex.
- SHA256/salt password writes remain the only set-password output path.
- Runtime gate remains open: known legacy-bug hash, canonical SHA1 hash, and
  current SHA256/salt password configs all authenticate as expected.
