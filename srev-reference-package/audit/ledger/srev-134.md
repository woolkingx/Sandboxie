### SREV-134: DriverAssist Clipboard Probe HGLOBAL Ownership

| Field | Content |
|---|---|
| Severity | [major] |
| Status | patched source-level after official GlobalAlloc / GlobalLock / SetClipboardData / EmptyClipboard review; needs Windows clipboard runtime proof |
| Evidence | `Sandboxie/core/svc/DriverAssistStart.cpp` was the highest-ranked unnamed reviewable core file after SREV-133. `DriverAssist::InitClipboard` creates dummy clipboard entries on Vista+ so driver-side `Gui_InitClipboard` can infer the internal clipboard item layout. `Sandboxie/core/drv/gui.c` says the service placed four unique clipboard items, then scans the kernel clipboard item array for format sequence `0x111111`, `0x222222`, `0x333333`, and `0x444444`. Before this SREV, the service created only two movable memory objects, reused each object for two clipboard formats, and dereferenced `GlobalLock` returns without checking `NULL`. Microsoft documents `GlobalAlloc` as returning `NULL` on failure; documents `GlobalLock` as returning a pointer and `NULL` on failure; documents `SetClipboardData` as placing a memory object on the clipboard with movable-memory requirements for memory objects; and documents `EmptyClipboard` as emptying the clipboard only while it is open. |
| Data | `Sandboxie/core/svc/DriverAssistStart.cpp`, `Sandboxie/core/drv/gui.c`, `DriverAssist::InitClipboard`, `Formats[4]`, four `HGLOBAL` probe objects, `GlobalAlloc`, `GlobalLock`, `GlobalUnlock`, `SetClipboardData`, `OpenClipboard`, `EmptyClipboard`, `CloseClipboard`, `GlobalFree`, `API_GUI_CLIPBOARD`, driver-side `Gui_InitClipboard`, and probe formats `0x111111`, `0x222222`, `0x333333`, `0x444444`. |
| Schema | `DRIVERASSIST_CLIPBOARD_PROBE_HGLOBAL_OWNERSHIP` says `InitClipboard` creates four unique movable memory objects for the four driver-probe clipboard formats; `GlobalAlloc` or `GlobalLock` failure prevents clipboard probing and still releases every allocated local object; `InitClipboard` dereferences a `GlobalLock` pointer only after it is non-null; `SetClipboardData` receives one unique `HGLOBAL` per private probe format; `API_GUI_CLIPBOARD` runs only after dummy clipboard items have been placed; the clipboard is emptied after the driver probe and before local dummy-object release; `Gui_InitClipboard` still observes the same four format markers in the same order; Vista+ probing and retry topology are unchanged. |
| Topology | Legal flow is Vista+ service startup, allocate four movable dummy `HGLOBAL` objects, lock/check/init/unlock each object, retry `OpenClipboard`, `EmptyClipboard`, place formats `0x111111` / `0x222222` / `0x333333` / `0x444444`, call `API_GUI_CLIPBOARD`, `EmptyClipboard`, `CloseClipboard`, then release local dummy objects. Driver observation remains `Gui_InitClipboard`, reference clipboard, require at least four items, scan the four format ids, and derive item length plus integrity index. |
| Logic Risk | The service and driver sides disagreed on the probe data shape: driver comments and scanner expect four unique dummy items, but the service reused two memory objects. Reusing clipboard memory objects makes ownership ambiguous around `SetClipboardData` and `EmptyClipboard`; unchecked `GlobalLock` can also crash the service under allocation or handle-state failure. The correct local repair is to make the service probe shape match the driver observation shape with four independent dummy objects and checked lock pointers. |
| Official Shape | `docs/plan/srev-134-driverassist-clipboard-probe-hglobal-ownership.md` records Microsoft `GlobalAlloc`, `GlobalLock`, `SetClipboardData`, and `EmptyClipboard` references. `docs/plan/srev-134-driverassist-clipboard-probe-hglobal-ownership.schema.json` records the JSON Schema draft-07 local `DRIVERASSIST_CLIPBOARD_PROBE_HGLOBAL_OWNERSHIP` contract. |
| Fix | `DriverAssist::InitClipboard` now allocates four `GMEM_MOVEABLE` `HGLOBAL` objects, initializes each only after `GlobalLock` returns a non-null pointer, and calls `SetClipboardData` once per format using the matching unique object. If allocation or lock initialization fails, the clipboard probe is skipped and every allocated dummy object is released. |
| Acceptance Gate | `docs/plan/check-srev-134.py` validates the draft-07 schema, official references, four unique dummy `HGLOBAL` slots, checked `GlobalAlloc` and `GlobalLock` topology, one `SetClipboardData` call per probe format through the `Formats` array, unchanged `API_GUI_CLIPBOARD` / `EmptyClipboard` / `CloseClipboard` order, driver-side four-format scanner evidence, and ledger entry; `docs/plan/check-srev-134.sh` is the matrix wrapper. Runtime/build gate: Windows service build for `DriverAssistStart.cpp`, Vista+ clipboard init smoke proving `API_GUI_CLIPBOARD` detects item length and integrity index, allocation failure injection proving no `GlobalLock` NULL dereference and no dummy object leak, clipboard-open retry smoke proving unopened clipboard leaves every local object freed, and ordinary clipboard operations proving integrity correction still works. |
