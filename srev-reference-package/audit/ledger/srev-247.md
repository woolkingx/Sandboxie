### SREV-247: DLL Hook WOW64 Stub Publish Gate

| Field | Content |
|---|---|
| Severity | [major] |
| Status | patched source-level after official executable-code review; needs Windows WOW64 runtime proof |
| Evidence | The pre-Windows 10 WOW64 path in `Dll_FixWow64Syscall` builds a 13-byte executable stub, then publishes it into the thread-specific WOW64 transition slot with `__writefsdword(0xC0, (ULONG)_code)`. Before this SREV, `_code = Dll_AllocCode128()` was not checked before writing stub bytes through `_code`, and the freshly generated executable stub was published without `FlushInstructionCache`. |
| Data | `Dll_FixWow64Syscall`, `_code`, `Dll_AllocCode128`, `X86SwitchTo64BitMode`, 13-byte WOW64 transition stub, `__writefsdword(0xC0, ...)`, `FlushInstructionCache`, `Dll_IsWow64`, `Dll_Windows`, pre-Windows 10 WOW64 thunk selection, and thread-specific `fs:[0xC0]` publication. |
| Schema | `DLLHOOK_WOW64_STUB_PUBLISH_GATE` says `Dll_FixWow64Syscall` owns the pre-Windows 10 WOW64 transition stub before it is published into `fs:[0xC0]`; `Dll_AllocCode128` may fail and must be gated before any stub byte write; the generated stub is executable code and must be flushed before publication; `__writefsdword(0xC0, ...)` is the publication edge for the current thread; the patch must not change the generated byte sequence, Windows 10 `wow64cpu` dispatcher hook path, NoSysCallHooks policy, or per-thread call topology. |
| Topology | Legal pre-Windows 10 path is `Dll_IsWow64 && Dll_Windows < 10`, read original `fs:[0xC0]` `X86SwitchTo64BitMode`, allocate executable 128-byte code slot, gate allocation success, write the 13-byte transition stub, `FlushInstructionCache(stub, 13)`, then publish the stub pointer into `fs:[0xC0]`. |
| Logic Risk | The WOW64 transition slot is a thread-local executable dispatch pointer. Writing through a failed allocation is an immediate null dereference. Publishing a freshly generated executable stub without a cache-coherency boundary can let the thread transition path observe stale or partially coherent instructions after Sandboxie reports the hook installed. |
| Official Shape | `docs/plan/srev-247-dllhook-wow64-stub-publish-gate.md` records Microsoft `FlushInstructionCache`, `VirtualProtect`, and `VirtualAlloc` references. `docs/plan/srev-247-dllhook-wow64-stub-publish-gate.schema.json` records the JSON Schema draft-07 local `DLLHOOK_WOW64_STUB_PUBLISH_GATE` contract. |
| Fix | `Dll_FixWow64Syscall` now returns if `Dll_AllocCode128` fails. After writing the 13-byte pre-Windows 10 WOW64 transition stub, it calls `FlushInstructionCache(GetCurrentProcess(), _code, 13)` before publishing `_code` through `__writefsdword(0xC0, ...)`. The source comment now points at this SREV as the owner of the 13-byte stub layout. |
| Acceptance Gate | `docs/plan/check-srev-247.py` validates the draft-07 schema, official reference links, source allocation gate before the first `_code` write, instruction-cache flush before `__writefsdword`, preservation of the generated byte sequence, source comment ownership of the generated byte sequence, preservation of the Windows 10 path, and the ledger fragment. Runtime/build gate: Windows 32-bit process under WOW64 on a pre-Windows 10 target or controlled compatibility VM proving the stub still routes syscalls through the intended thunk, plus allocation-failure injection proving the path returns without writing through NULL. |
